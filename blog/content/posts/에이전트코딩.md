대략... 

* yaml: ...즉시 구현가능한 구조화된 명세서 작성...
* 목적:

* 작업단계 WorkFlow:
    1. 클래스와 책임을 명확히 한다.

    3. 요구 상태 결정: 추론이냐 유저가 명시했느냐

`requirement-organizer` 스킬은 매우 중요하다.

```txt
이 문서는 `requirement-organizer`라는 **소프트웨어 요구사항 정리용 지침(스킬)**입니다.

핵심 목적은 사용자가 대화식으로 흩어놓은 요구사항을 곧바로 설계하거나 구현하지 않고, 
다음 단계에서 검토하기 쉬운 **상위 수준의 책임 개요**로 정리하는 것입니다.

주요 내용은 다음과 같습니다.

- 중복되거나 장황한 표현을 제거하되 사용자의 의도는 보존합니다.
- 시스템이 담당해야 할 핵심 책임을 분류합니다.
- 각 책임을 맡을 수 있는 클래스나 컴포넌트의 **후보 이름**을 제안합니다.
- 화면이 있는 프로그램이라면 다음을 명확히 분리합니다.
  - 핵심 시스템 책임
  - UI 책임
  - UI와 시스템 사이에 오가는 개념적 정보
  - 앱 시작점이나 전체 연결 등 후속 통합 작업
- 아직 결정되지 않은 중요한 사항은 `미정 사항`에 기록합니다.
- 결과는 한국어로 작성하되, `OrderManager` 같은 기술 식별자는 영어를 사용할 수 있습니다.

예를 들어 다음 요구사항이 있다면:

> 잘못된 입력으로는 주문할 수 없게 하고 오류를 보여주세요.

다음처럼 나눕니다.

- 핵심 시스템
  - 주문 가능한 입력인지 판단한다.
  - 주문할 수 없는 이유를 구분한다.
- UI
  - 사용자의 입력을 받는다.
  - 주문할 수 없는 이유를 화면에 표시한다.
- 시스템 경계
  - UI가 주문 의도와 입력값을 전달한다.
  - 시스템이 처리 결과나 오류 종류를 반환한다.

이 지침에서 의도적으로 정하지 않는 것도 많습니다.

- 메서드명, 매개변수, 반환값
- 멤버 변수와 자료구조
- 알고리즘과 디자인 패턴
- 데이터베이스 스키마와 API 규격
- 프레임워크와 라이브러리
- 구체적인 화면 구조와 디자인
- 파일 구성과 담당 개발자
- 최종 구현 아키텍처

즉, 이 문서의 요지는 다음 한 문장으로 정리할 수 있습니다.

> **비정형 요구사항을 구현 설계로 넘어가기 전 단계의 ‘책임 지도’로 정리하라.**

결과물은 대략 `핵심 시스템 책임 → UI 책임 → 시스템 경계 → 후속 통합 항목 → 미정 사항` 순서의 한국어 Markdown 문서가 됩니다. UI가 없는 기능이라면 UI 및 시스템 경계 부분은 생략합니다.
```


### 3. 에이전트 정하기

에이전트는 대략 내가 하려는 작업에 따라 
거의 스킬을 하나씩 장착한 대로 만들면 되겠지만
UI 구현과 로직 구현을 분리할시 같은 파일에 대한 수정이 이루어져 좋진 않았다

그래서

```txt
1. organizer => (skill)requirement-organizer
2.1. spec-writer=> (skill)class-spec-writer
2.2. designer=>(skill) web-design-director
3. coder => (skill) code-implementer + frontend-implementer
4. tester 
```
이런 형태로 구성했다. 코더는 스킬을 2개를 가지고 구현을 전담한다. 
대신 상세스펙들을 읽고 충실히 구현만 한다. 

### 4. 작업절차

가장 중요한 부분이고 가장 어려운거 같다. 

```markdown
## 에이전트 파이프라인

'''
organizer ─→ spec-writer ───┐
         └─→ design-director ┴─→ coder ─→ tester
'''

| 에이전트 | 역할 | 산출물 |
|----------|------|--------|
| `organizer` | 사용자와 대화하며 요구사항 정리 (requirement-organizer 스킬, primary) | `docs/requirements.md` |
| `spec-writer` | 파서/모델/렌더러 클래스 명세 (class-spec-writer 스킬) | `docs/specs/` |
| `design-director` | 렌더링 페이지 디자인 명세 (web-design-director 스킬) | `docs/design/` |
| `coder` | 명세 기반 기능 + HTML/CSS 템플릿 구현, 구현 후 빌드 검증 | `src/` |
| `tester` | 문제 재현·원인 진단과 파서 정확성·재생성 무결성·링크 유효성 검증 | `src/tests/` |

명세 산출물이 다음 단계 에이전트의 입력 계약이다. organizer의 요구사항 개요를 받아 스펙/디자인은 병렬 진행 가능하고, 구현은 영향받는 명세가 모두 준비된 후 시작한다.

### 파이프라인 운영 원칙

- 모든 신규 기능, 변경 요청, 문제 보고는 `organizer`를 통해 접수한다.
- `AGENTS.md`는 단계 순서와 전환 조건의 단일 진실 공급원이다. 개별 에이전트 정의는 자신의 역할, 입력, 출력, 수정 범위와 금지 사항만 구체화한다.
- 각 에이전트는 자신의 산출물 범위 밖의 파일을 수정하지 않는다.
- 하위 에이전트는 입력 계약에 없는 내용을 임의로 결정하거나 상위 산출물을 직접 수정하지 않고 `organizer`에게 반환한다.
- 사용자의 직접 요청이 현재 산출물 계약과 충돌하면 작업을 진행하지 않고 충돌 내용을 `organizer`에게 보고한다.

### 신규 기능·변경 요청 절차

1. `organizer`가 사용자의 의도, 기대 결과, 제약, 미정 사항을 정리한다.
2. 사용자가 확인한 요구사항만 `docs/requirements.md`에 반영한다.
3. 핵심 시스템 책임이 바뀌면 `spec-writer`, UI 책임이 바뀌면 `design-director`가 각각의 명세를 갱신한다. 두 영역이 모두 영향받으면 두 에이전트가 모두 작업한다.
4. `coder`는 갱신된 `docs/specs/`와 `docs/design/`을 구현 계약으로 삼아 영향 범위만 구현한다.
5. `tester`가 변경 요청, 기존 기능, 빌드 재생성을 검증한다.
6. `organizer`가 검증 결과와 남은 문제를 사용자에게 보고한다.

### 문제 보고·결함 수정 절차

1. `organizer`가 보고된 현상, 기대 결과, 실제 결과, 재현 조건과 관련 증거를 정리한다.
2. 구현을 수정하기 전에 `tester`에게 재현과 원인 분석을 요청한다. 진단 요청에서는 프로덕션 코드와 명세를 수정하지 않는다.
3. `organizer`가 진단 결과를 기존 요구사항 대비 구현 결함, 명세·디자인 누락, 새로운 요구사항 중 하나로 분류한다.
4. 구현 결함이면 요구사항을 변경하지 않고 `coder`에게 기존 계약과 진단 결과를 전달한다.
5. 명세·디자인 누락이면 요구사항과 진단 결과를 담당 에이전트에게 전달해 명세를 먼저 보완한다.
6. 새로운 요구사항이면 사용자 확인 후 `docs/requirements.md`부터 갱신하고 신규 기능·변경 요청 절차를 따른다.
7. 수정 후 `tester`가 재현 조건과 관련 회귀 범위를 검증한다.

### 단계 실패 반환 규칙

- 하위 에이전트가 모호함, 계약 충돌, 입력 누락을 발견하면 작업을 임의로 완성하지 않고 근거와 필요한 결정을 `organizer`에게 보고한다.
- `tester`가 실패를 보고하면 `organizer`가 실패 원인을 분류한 후 요구사항, 명세, 디자인, 구현 중 해당 단계로 되돌린다.
- 실패가 발생했다는 이유로 `organizer`가 코드, 클래스 명세, 디자인 명세를 직접 수정하지 않는다.
```

즉 프로젝트가 어떤 절차로 흘러가야 하는지를 정하는 것이다.
물론 내가 만든것이 아니고 GPT가 만들었다...
