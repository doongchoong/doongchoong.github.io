잠깐의 오류로 요청이 실패했을 때 재시도를 넣는 것은 그렇게 어렵지 않다. 하지만 Client가 하나가 아니라면 어떨까? 모두 같은 시각에 실패하고 같은 규칙으로 재시도하면, 재시도 자체가 다음 부하를 만들 것 같았다.

고정 간격, Exponential Backoff, Jitter를 Python으로 간단하게 시뮬레이션해서 요청이 시간에 따라 어떻게 퍼지는지 확인해보았다.

1. 재시도 방식

1.1. 고정 간격

가장 단순한 방식은 항상 같은 시간을 기다리는 것이다. 예를 들어 1초를 사용하면 모든 Client가 1초, 2초, 3초에 다시 요청한다.

PY
def fixed_delay(attempt, rng):
    return 1.0

하나의 Client만 보면 예측하기 쉽다. 하지만 여러 Client가 동시에 시작했다면 처음에 생긴 정렬이 계속 유지된다.

1.2. Exponential Backoff

Exponential Backoff는 실패할 때마다 대기 시간을 두 배씩 늘린다. 장애가 길어질수록 요청 횟수를 줄일 수 있고, 대기 시간이 끝없이 늘지 않도록 상한을 둔다.

PY
def exponential_delay(attempt, rng):
    return min(0.5 * 2 ** (attempt - 1), 8.0)

이번 설정에서 대기 시간은 0.5, 1, 2, 4, 8...초가 된다. 재시도 횟수는 확실히 줄지만 모든 Client가 같은 규칙을 사용하면 여전히 같은 시각에 몰린다. 간격만 멀어진 것이다.

1.3. Jitter

Jitter는 대기 시간에 무작위성을 추가한다. 이번에는 Exponential Backoff로 구한 상한과 0 사이에서 무작위로 기다리는 Full Jitter를 사용했다.

PY
def jitter_delay(attempt, rng):
    ceiling = min(0.5 * 2 ** (attempt - 1), 8.0)
    return rng.uniform(0, ceiling)

같은 횟수의 재시도라도 Client마다 기다리는 시간이 달라진다. 정렬을 깨는 핵심은 Backoff의 크기보다 이 무작위성에 있다.

2. 시뮬레이션 설계

Client 200개가 0초에 모두 실패했다고 가정했다. 서버는 4초에 회복하며, Client는 회복 이후의 첫 요청에서 성공하고 더 이상 재시도하지 않는다. 난수 seed는 20260829로 고정했고, 요청은 100ms 구간으로 묶어서 세었다.

최초 0초의 실패 요청은 어떤 방식이든 200개로 같다. 그래서 이 요청은 빼고 재시도가 만든 분포만 비교했다.

핵심 시뮬레이션은 다음과 같다.

PY
def simulate(client_count, delay_fn, recovered_at, rng):
    events = []
    success_times = []

    for _ in range(client_count):
        now = 0.0

        for attempt in range(1, 21):
            now += delay_fn(attempt, rng)
            events.append(now)

            if now >= recovered_at:
                success_times.append(now)
                break

    return events, success_times

실제 서버의 처리량이나 응답 지연은 모델링하지 않았다. 이 실험에서 궁금한 것은 재시도 규칙 자체가 Client들을 얼마나 퍼뜨리는지이다.

3. 그래프

아래 그래프는 각 100ms 구간에 들어온 요청 수를 나타낸다. 세로축을 모두 200으로 맞춰서 몰림의 크기를 같은 기준으로 비교했다.

고정 간격은 1초마다 200개의 요청이 정확히 동시에 생긴다. 서버가 4초에 회복했으니 모든 Client가 바로 성공하지만, 회복한 순간에 다시 200개를 받아야 한다.

Exponential Backoff의 요청은 0.5초, 1.5초, 3.5초, 7.5초에 생긴다. 요청 간격은 점점 늘었지만 세로 막대의 높이는 그대로다. 게다가 서버는 4초에 이미 회복했는데 다음 재시도는 7.5초에 있어서 3.5초를 더 기다렸다.

Full Jitter는 모양이 완전히 다르다. 초반에는 요청이 많지만 재시도가 진행될수록 여러 구간으로 퍼진다. 100ms 구간에 가장 많이 들어온 요청도 60개였고, 서버 회복 이후에는 최대 8개였다.

4. 결과

고정 간격 800 200 4.000초 4.000초 4.00
Exponential Backoff 800 200 7.500초 7.500초 4.00
Full Jitter 925 60 5.843초 10.442초 4.62

예상했던 것처럼 Exponential Backoff만으로는 Client의 동시성이 사라지지 않았다. 오히려 장애 중 요청 횟수를 줄이는 역할에 가깝다.

Jitter는 몰림을 확실히 줄였다. 하지만 무작위 범위가 0부터 시작하기 때문에 아주 짧은 대기 시간이 연속으로 나올 수 있다. 그 Client들은 서버가 회복하기 전에 요청을 더 많이 소비했고, 반대로 긴 대기 시간을 연속으로 뽑은 Client는 성공까지 더 오래 걸렸다.

그래서 이번 실행에서 Full Jitter의 전체 재시도는 925개로 늘었고, 95%의 Client가 성공하는 시점도 10.442초로 느려졌다. 이 수치만 보면 Jitter가 손해처럼 보일 수 있다. 하지만 실제 서버에서는 200개가 한번에 재진입하는 것과 여러 시각에 나누어 들어오는 것이 같지 않다. 이번 모델에는 그 차이를 성공률이나 응답 시간으로 반영하지 않았다.

5. 생각해볼점

이번 시뮬레이션으로 보면 Exponential Backoff와 Jitter는 서로 대체하는 방식이 아니다. Backoff는 장애가 계속될 때 요청 빈도를 낮추고, Jitter는 여러 Client의 시계를 엇갈리게 한다. 둘을 같이 사용해야 각자의 역할이 드러난다.

다만 Jitter를 넣었다고 끝은 아니다. 서버가 알려준 재시도 시각이 있다면 그 값을 우선해야 하고, 요청을 다시 보내도 안전한지도 따로 확인해야 한다. 재시도 횟수와 최대 대기 시간도 필요하다.

다음에는 서버에 100ms당 처리량을 넣고 싶다. 그렇게 하면 이번에는 그래프의 모양으로만 보았던 “몰림”이 실제 성공률과 회복 시간에 어떤 차이를 만드는지도 볼 수 있을 것 같다.
